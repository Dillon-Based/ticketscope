## Intent

**Problem:** The CNPG Cluster has no backups. R5 is met only when CI on kind shows a backup completing to SeaweedFS through the Barman Cloud Plugin (AD-18), with the endpoint in `values-kind.yaml` and the credentials in a chart-generated Secret (AD-25), so that epic-eks-environment can later point the same values at S3.

**Approach:** The platform release gains the Barman Cloud Plugin, which is always on, and SeaweedFS, which only `values-kind.yaml` enables. The ticketscope release gains an `ObjectStore` and turns on the Cluster's plugin WAL archiver. A new `kind` smoke test takes an on-demand `Backup`, waits for phase `completed`, and lists the backup's objects in the SeaweedFS bucket.

## Boundaries & Constraints

**Always:**
- Use the Barman Cloud Plugin (CNPG-I, `barman-cloud.cloudnative-pg.io`), chart `cnpg/plugin-barman-cloud` 0.8.1 (app v0.15.1), and SeaweedFS chart 4.52.0. Both are dependencies of `deploy/charts/platform`, and `Chart.lock` is regenerated and committed.
- The plugin runs in the `platform` namespace beside the CNPG operator, because the operator finds plugins by Service in its own namespace.
- Do not add cert-manager. Set the plugin chart's `certificate.createIssuer`, `createServerCertificate` and `createClientCertificate` to false. The platform chart generates the Secrets `barman-cloud-server-tls` (CN and SAN `barman-cloud`) and `barman-cloud-client-tls` itself: self-signed, of type `kubernetes.io/tls`, with `tls.crt`, `tls.key` and `ca.crt`. They are kept across upgrades through `lookup`, like `ticketscope-db-ro`.
- The S3 credentials are generated by a chart. Neither repo values nor git hold any key.
- `values-kind.yaml` files hold only environment facts (AD-25): SeaweedFS on/off and its storage class, the backup endpoint and destination path, and where the credentials come from. Every other default sits in `values.yaml`.
- `instances: 2` and the existing Cluster settings stay unchanged.

**Never:**
- No in-tree `barmanObjectStore` (it was removed in CNPG 1.32). No ScheduledBackup, no restore or failure drill, and no EKS/S3/IRSA wiring beyond a values shape that can hold it (epic-eks-environment).
- No OTel, Tempo or Grafana (story 9). Do not create a cert-manager dependency or a separate Helm release.
- Do not expose SeaweedFS outside the cluster: no HTTPRoute, no Ingress, and no LoadBalancer Service.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| On-demand backup | `Backup` with `method: plugin` on `ticketscope-db` after kind-up | Phase `completed`. The bucket lists objects under the backup's `<serverName>/base/<backupId>/` | The test fails with the Backup's status and error if the phase is `failed` or the timeout passes |
| Fresh platform install | No cert-manager CRDs in the cluster | `platform --wait` succeeds, the plugin Deployment is Ready, and the bucket exists | — |
| Re-run kind-up / upgrade | Existing TLS and credential Secrets | The Secrets are unchanged, so no new certs or keys, and existing backups stay readable | — |
| Platform missing | ticketscope installed on a cluster that has CNPG but not the platform credential Secret | The render fails with a message naming the platform release | Fail the Helm render; never install an ObjectStore with empty keys |
| Offline render | `helm lint` / `helm template` (no cluster) | Renders cleanly with both values files | — |

## Design Notes

- **Why no cert-manager.** The plugin chart's Issuer and Certificates need cert-manager CRDs. In a single release those CRDs are templates, so a fresh `helm install` fails to map the kinds. Helm-generated self-signed certs carry the same Secret names and keys the plugin Deployment and the operator's Service annotations (`cnpg.io/pluginServerSecret`, `cnpg.io/pluginClientSecret`) read, which keeps it to two releases (AD-13).
- **Why copy the credentials.** The ObjectStore's Secret must sit in the Cluster's namespace, but SeaweedFS's chart generates its keys in `platform`. Install order is binding (AD-22: platform first), so the ticketscope chart copies the keys through `lookup` at render time. On EKS, `copyFrom` stays empty and `inheritFromIAMRole: true` replaces it.
- **WAL archiving is required.** A plugin backup completes only once its end WAL is archived, so the Cluster must name the plugin as `isWALArchiver`.
